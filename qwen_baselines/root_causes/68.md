* **Violated property / error message:**

  `gov.nasa.jpf.vm.NoUncaughtExceptionsProperty`

  `java.lang.NullPointerException: Calling 'growScale()V' on null object`

* **Location (file:line):**

  `Main.java:6`

  Specifically:

  ```java

  ```

* **Counterexample summary (threads, key steps):**

  1. `main()` creates a `DragonScaleCounter` and assigns it to the local variable `counter`.
  2. `main()` creates `t1` and `t2`, each using a lambda that captures `counter`, and starts both.
  3. JPF enters `Main$$Lambda$0.run`, the synthetic class generated for `t1`'s lambda, which delegates to `Main.lambda$main$0`.
  4. The receiver of `growScale()` is null. This happens on the first execution of `t1`'s loop body (search depth 5, 5 new states), before any interleaving choice matters.
  5. The search stops at the first error. `t2`'s lambda uses the same construct.

## 3. Root cause

**Shared state** *(variable / object / lock):*

n/a as a concurrency bug.

The real shared state is `MysticCAS.value`, which is accessed only through `synchronized` methods. The failing reference is the captured `counter` inside the lambda executed by `t1`.

**Accesses involved**

| Thread | Method               | Line | Operation (R/W/lock/wait/notify)              |
| ------ | -------------------- | ---- | --------------------------------------------- |
| `t1`   | `Main.lambda$main$0` | 6    | Method invocation on null `counter` reference |
| n/a    | n/a                  | n/a  | n/a                                           |

**Guarantee that is missing** *(what should be atomic, ordered, or protected):*

None at the program level. `get()` and `compareAndSwap()` are both `synchronized`, so the check-and-set is atomic. A failed CAS returns a value different from `expected`, and a successful CAS returns exactly `expected`, so the `!= old` retry condition is correct. `Thread.start()` also gives a happens-before edge, so `counter` is safely visible to the new threads. The missing guarantee is in the tool's handling of lambda capture.

**Buggy interleaving** *(2 to 4 steps)*

n/a. The failure is not caused by a concurrency interleaving between conflicting shared accesses.

**Why this produces the JPF symptom:**

In the source program, `counter` is initialized with:

```java
DragonScaleCounter counter = new DragonScaleCounter();
```

and is never assigned `null`. Nevertheless, JPF reports that the receiver of `growScale()` in `Main.lambda$main$0` is null.

A lambda capturing `counter` compiles to `invokedynamic`, and JPF synthesizes a `Main$$Lambda$0` class to carry the captured value. The null receiver inside the synthetic body suggests the captured `counter` was not propagated correctly. This is an inference from the stack trace and from the fix (anonymous classes, which use ordinary constructor and field capture, eliminate the error). The exact JPF mechanism was not verified.

There is no evidence in the supplied source of an application-level defect.

## 4. Suggested solution

**Fix type**

* [ ] Add or widen synchronization (synchronized / lock)
* [ ] Use an atomic or concurrent class
* [ ] Add volatile
* [ ] Change lock order / lock granularity
* [ ] Fix wait/notify (condition loop, notifyAll, missing signal)
* [ ] Thread confinement or immutability
* [x] Other: **Replace the lambdas with explicit `Runnable` implementations (anonymous classes)**

**Where to apply it** *(file:line range)*:

`Main.java:4-15`, covering both lambdas: `t1` (lines 4-9) and `t2` (lines 10-15).

**Description of the fix:**

Replace both lambda expressions with anonymous `Runnable` classes so that `counter` is passed through an ordinary synthetic field set by the constructor instead of being captured by a lambda. `MysticCAS` and `DragonScaleCounter` are unchanged.

The fix also declares `counter` as `final`. This is cosmetic, since the variable was already effectively final. The behavioral change is lambda → anonymous class.

**Code sketch**

```java
// before

Thread t1 = new Thread(() -> {
    for (int i = 0; i < 100; i++) {
        counter.growScale();
    }
    System.out.println("Thread 1 done");
});
```

```java
// after

final DragonScaleCounter counter = new DragonScaleCounter();

Thread t1 = new Thread(new Runnable() {
    @Override
    public void run() {
        for (int i = 0; i < 100; i++) {
            counter.growScale();
        }
        System.out.println("Thread 1 done");
    }
});
// t2 is changed in the same way
```

**Why it removes the symptom:**

n/a as an interleaving fix. An anonymous inner class compiles to an ordinary class (`Main$1`, `Main$2`) that stores `counter` in a synthetic field set through its constructor. This uses plain `new`, `putfield` and `getfield` bytecodes, avoiding the lambda-generated bytecode path that appears to produce the null receiver under JPF.

**Validation:**

Fix applied (lambdas → anonymous `Runnable`s, no logic change): the reported NPE no longer occurs and the run passes JPF.

**Other acceptable fixes** *(there is often more than one)*:

Use named classes implementing `Runnable`, or otherwise restructure the thread entry points so that `counter` is passed without lambda capture.

**Invalid or superficial fixes for this bug:**

* Making `growScale()` synchronized
* Adding `volatile` to `MysticCAS.value`
* Replacing `MysticCAS` with `AtomicInteger` (a different design; the NPE is not in the counter)
* Adding `final` to `counter` (already effectively final)
* Adding `Thread.sleep()`
* Reducing the loop count or number of threads

None of these addresses the reported null receiver.
