## 3. Root cause

**Shared state:** `BoundedBuffer.items`, `putPtr`, `takePtr` and `count`, all guarded by the buffer's monitor (`synchronized (this)`). Capacity is guarded by two `Semaphore`s, `availableSpaces` (initially 1) and `availableItems` (initially 0).

**Accesses involved**

| Thread        | Method   | Line | Operation                                                       |
| ------------- | -------- | ---- | --------------------------------------------------------------- |
| pool-thread-1 | `put(1)` | n/a  | acquire `availableSpaces`, W under lock, release `availableItems` |
| pool-thread-2 | `take()` | n/a  | acquire `availableItems`, R/W under lock, release `availableSpaces` |

**Guarantee that is missing:** none. Every access to buffer state is under the same monitor. The semaphore protocol is the standard bounded-buffer pattern: `put` blocks until a space exists, `take` blocks until an item exists. Both orderings of the two threads terminate, so there is no deadlock and no lost wakeup. `isEmpty()` and `isFull()` are never called.

**Buggy interleaving:** n/a. No faulty interleaving exists.

**Why this produces the JPF symptom (hypothesis, unconfirmed):**

1. The driver uses `Executors.newFixedThreadPool(2)` and a timed `awaitTermination(1, SECONDS)`. These pull in `ThreadPoolExecutor`, `LinkedBlockingQueue`, AQS and timed waits, which JPF models poorly, and every internal step is a scheduling point.
2. `Semaphore` is also AQS-based, which adds more scheduling points.
3. The program's own workload is tiny, so this alone is an unlikely cause of state explosion. The executor internals are the more likely culprit.

## 4. Suggested solution

**Fix type**

* [ ] Add or widen synchronization
* [ ] Use an atomic or concurrent class
* [ ] Add volatile
* [ ] Change lock order / lock granularity
* [ ] Fix wait/notify
* [ ] Thread confinement or immutability

**Where to apply it:** `Main.main()`. `BoundedBuffer` stays unchanged. The wildcard import is also narrowed to `java.util.concurrent.Semaphore`.

**Description of the fix:** Replace the executor with two plain `Thread` objects (one `put`, one `take`) and `join()` them. Both threads and both operations are kept, so the concurrency under test is unchanged. This is a workaround for JPF's limits, not a concurrency fix.

**Code sketch**

```java
// before
ExecutorService es = Executors.newFixedThreadPool(2);
es.execute(() -> { try { buffer.put(1); } catch (InterruptedException e) { Thread.currentThread().interrupt(); } });
es.execute(() -> { try { buffer.take(); } catch (InterruptedException e) { Thread.currentThread().interrupt(); } });
es.shutdown();
es.awaitTermination(1, TimeUnit.SECONDS);
```

```java
// after
Thread t1 = new Thread(() -> { try { buffer.put(1); } catch (InterruptedException e) { Thread.currentThread().interrupt(); } });
Thread t2 = new Thread(() -> { try { buffer.take(); } catch (InterruptedException e) { Thread.currentThread().interrupt(); } });
t1.start(); t2.start();
t1.join(); t2.join();
```

**Why it removes the symptom:** Plain threads avoid the `ThreadPoolExecutor` and timed-wait machinery, so the search has far fewer scheduling points and can terminate. No shared-state access changes, because the buffer was already correct.

**Other acceptable fixes:**

* Keep the executor but replace the timed `awaitTermination(1, SECONDS)` with an untimed one, or raise JPF's `search.depth_limit`.
* If the Semaphore itself turns out to be the problem, replace it with a `wait()/notifyAll()` condition loop. This is a larger redesign and is not minimal.

**Invalid or superficial fixes for this case:**

* Treating the harness change as a repair of a concurrency bug. The original program has no bug.
* Adding extra locks or making `put`/`take` fully `synchronized`. That would hold the monitor while blocked on a semaphore and could introduce a real deadlock.
* Removing one of the threads, which removes the concurrency under test.
