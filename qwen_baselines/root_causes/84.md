## 3. Root cause

**Shared state** *(variable / object / lock):*

n/a as a concurrency bug.

The real shared state is the `ConcurrentHashMap` inside `DelegatingVehicleTracker`. The failing reference is the captured `tracker` inside the lambda executed by a pool worker.

**Accesses involved**

| Thread       | Method               | Line | Operation (R/W/lock/wait/notify)              |
| ------------ | -------------------- | ---- | --------------------------------------------- |
| pool worker  | `Main.lambda$main$0` | 1    | Method invocation on null `tracker` reference |
| n/a          | n/a                  | n/a  | n/a                                           |

**Guarantee that is missing** *(what should be atomic, ordered, or protected):*

None at the program level. `ConcurrentHashMap.replace` is atomic, `Point` is immutable, and `getLocationsAsStatic()` copies from a thread-safe map. `ExecutorService.execute` gives a happens-before edge from submission to execution, so `tracker` is safely visible to the workers even without `final`. No task dereferences the result of `getLocation("2")`, which returns `null` for an absent key, and `setLocation("1", ...)` targets a key that exists, so no `IllegalArgumentException` is expected. The missing guarantee is in the tool's handling of lambda capture.

**Buggy interleaving** *(2 to 4 steps)*

n/a. The failure is not caused by a concurrency interleaving between conflicting shared accesses.

**Why this produces the JPF symptom:**

In the source program, `tracker` is initialized with:

```java
DelegatingVehicleTracker tracker = new DelegatingVehicleTracker(initial);
```

and is never assigned `null`. Nevertheless, JPF reports that the receiver of `setLocation()` in `Main.lambda$main$0` is null.

A lambda capturing `tracker` compiles to `invokedynamic`, and JPF synthesizes a `Main$$Lambda$0` class to carry the captured value. The null receiver inside the synthetic body suggests the captured `tracker` was not propagated correctly. This is an inference from the stack trace and from the fix (anonymous classes, which use ordinary constructor and field capture, eliminate the error). The exact JPF mechanism was not verified.

The executor itself worked: JPF created all five workers and ran `ThreadPoolExecutor.runWorker` up to the task. The NPE occurs inside the lambda body, not inside the pool code. This suggests the lambda change, rather than the removal of the executor, is what fixes this case.

## 4. Suggested solution

**Fix type**

* [ ] Add or widen synchronization (synchronized / lock)
* [ ] Use an atomic or concurrent class
* [ ] Add volatile
* [ ] Change lock order / lock granularity
* [ ] Fix wait/notify (condition loop, notifyAll, missing signal)
* [ ] Thread confinement or immutability
* [x] Other: **Replace the lambdas with explicit `Runnable` implementations (anonymous classes)**

**Where to apply it** *(file:line range)*:

`Main.main`, covering all five task lambdas. The old source is on a single line, so line ranges are not meaningful. `Point` and `DelegatingVehicleTracker` are unchanged.

**Description of the fix:**

Replace each lambda with an anonymous `Runnable` and declare `tracker` as `final`. The supplied fixed version also replaces the executor with five plain `Thread`s started and joined directly, and writes `java.util.concurrent.ConcurrentHashMap` fully qualified instead of importing `java.util.concurrent.*`. The `final` and the qualified name are cosmetic.

Based on the stack trace, the lambda → anonymous class change is the one that matters. The executor swap is probably not needed here, but that variant was not tested.

**Code sketch**

```java
// before

DelegatingVehicleTracker tracker = new DelegatingVehicleTracker(initial);
ExecutorService es = Executors.newFixedThreadPool(5);
es.execute(() -> { tracker.setLocation(String.valueOf(1), 1, 1); });
// four more lambdas
es.shutdown();
es.awaitTermination(1, TimeUnit.SECONDS);
```

```java
// after

final DelegatingVehicleTracker tracker = new DelegatingVehicleTracker(initial);

Thread t1 = new Thread(new Runnable() {
    public void run() {
        tracker.setLocation(String.valueOf(1), 1, 1);
    }
});
// t2 to t5 are changed in the same way
t1.start();
// start t2 to t5
t1.join();
// join t2 to t5
```

**Why it removes the symptom:**

n/a as an interleaving fix. An anonymous inner class compiles to an ordinary class that stores `tracker` in a synthetic field set through its constructor. This uses plain `new`, `putfield` and `getfield` bytecodes, avoiding the lambda-generated bytecode path that appears to produce the null receiver under JPF.

**Validation:**

The supplied fixed version (anonymous `Runnable`s, plain threads, `final tracker`) is taken as passing JPF per the case record. This was not re-run here. Which of the two main changes (lambdas → anonymous classes, executor → plain threads) is responsible is not isolated by the evidence, although the failing frame points to the lambda.

**Other acceptable fixes** *(there is often more than one)*:

* Keeping the executor but replacing the lambdas with anonymous `Runnable`s (not tested).

**Invalid or superficial fixes for this bug:**

* Adding `volatile`
* Adding `final` to `tracker` alone (already effectively final)
* Changing the map type or the snapshot method
* Changing the pool size or `awaitTermination` timeout
* Adding `Thread.sleep()`

None of these addresses the reported null receiver.
