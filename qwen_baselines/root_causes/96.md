## 3. Root cause

**Shared state:** `StripedMap.buckets[]` (bucket heads and their `Node` chains), guarded by the striped lock array `locks[16]`. Bucket `i` is guarded by `locks[i % 16]`.

**Accesses involved**

| Thread        | Method      | Line | Operation                                    |
| ------------- | ----------- | ---- | -------------------------------------------- |
| pool-thread-1 | `put(1, 2)` | n/a  | W `buckets[1]` under `locks[1]`              |
| pool-thread-2 | `get(1)`    | n/a  | R `buckets[1]` chain under `locks[1]`        |
| pool-thread-3 | `put(3, 4)` | n/a  | W `buckets[3]` under `locks[3]`              |
| pool-thread-4 | `clear()`   | n/a  | W `buckets[0..3]`, one lock at a time        |

**Guarantee that is missing:** none. With 4 buckets and 16 locks, `i % 16 == i`, so every bucket has its own lock and every access to a bucket holds that bucket's lock. No method holds more than one lock at a time, so there is no lock-order cycle. `buckets.length` is read outside a lock, but the array reference is `final` and its length never changes.

**Buggy interleaving:** n/a. No faulty interleaving exists. `clear()` is not atomic across buckets, but that is a design choice and nothing in the program checks for it.

**Why this produces the JPF symptom (hypothesis, unconfirmed):**

1. The driver uses `Executors.newFixedThreadPool(4)` and a timed `awaitTermination(1, SECONDS)`. These pull in `ThreadPoolExecutor`, `LinkedBlockingQueue`, AQS and timed waits, which JPF models poorly, and every internal step is a scheduling point.
2. Four worker threads multiply the interleavings. The program's own workload is small, so the executor internals are the more likely culprit.

## 4. Suggested solution

**Fix type**

* [ ] Add or widen synchronization
* [ ] Use an atomic or concurrent class
* [ ] Add volatile
* [ ] Change lock order / lock granularity
* [ ] Fix wait/notify
* [ ] Thread confinement or immutability

**Where to apply it:** `Main.main()`. `StripedMap` stays unchanged. The `java.util.concurrent` import is removed because it is no longer used.

**Description of the fix:** Replace the executor with four plain `Thread` objects running the same four operations, and `join()` them. All four threads and all four operations are kept, so the concurrency under test is unchanged. This is a workaround for JPF's limits, not a concurrency fix.

**Code sketch**

```java
// before
ExecutorService es = Executors.newFixedThreadPool(4);
es.execute(() -> { map.put(1, 2); });
es.execute(() -> { map.get(1); });
es.execute(() -> { map.put(3, 4); });
es.execute(() -> { map.clear(); });
es.shutdown();
es.awaitTermination(1, TimeUnit.SECONDS);
```

```java
// after
Thread t1 = new Thread(() -> { map.put(1, 2); });
Thread t2 = new Thread(() -> { map.get(1); });
Thread t3 = new Thread(() -> { map.put(3, 4); });
Thread t4 = new Thread(() -> { map.clear(); });
t1.start(); t2.start(); t3.start(); t4.start();
t1.join(); t2.join(); t3.join(); t4.join();
```

**Why it removes the symptom:** Plain threads avoid the `ThreadPoolExecutor` and timed-wait machinery, so the search has far fewer scheduling points and can terminate. No shared-state access changes, because the map was already correctly locked.

**Other acceptable fixes:**

* Keep the executor but replace the timed `awaitTermination(1, SECONDS)` with an untimed one, or raise JPF's `search.depth_limit`.
* If the search still does not terminate with plain threads, reduce to 3 threads. Record this as a weaker workaround, since it shrinks the workload.

**Invalid or superficial fixes for this case:**

* Treating the harness change as a repair of a concurrency bug. The original program has no bug.
* Replacing the striped locks with one global lock, or making all methods `synchronized`. That removes the striping the program is built around.
* Removing the `clear()` thread, which removes the concurrency under test.
