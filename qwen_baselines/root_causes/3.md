## 3. Root cause

**Shared state** *(variable / object / lock):*

`CountingFireflies.asleep`, a mutable field of the single shared `CountingFireflies` instance `scout`.

**Accesses involved**

| Thread   | Method               | Line | Operation (R/W/lock/wait/notify) |
| -------- | -------------------- | ---- | -------------------------------- |
| Thread-1 | `tryToSleep()`       | 5    | R (`while (!asleep)`)            |
| Thread-2 | `setAsleep(boolean)` | 20   | W (`this.asleep = value`)        |

**Guarantee that is missing** *(what should be atomic, ordered, or protected):*

The conflicting read and write of the shared variable `asleep` should be protected by a common synchronization mechanism so that the accesses cannot occur concurrently under JPF's race-detection model.

**Buggy interleaving** *(2 to 4 steps)*

1. Thread-1 enters `tryToSleep()` and reads `scout.asleep` while it is `false`.
2. Thread-1 continues executing the loop and accessing the shared field.
3. Thread-2 finishes its 500 ms delay and calls `scout.setAsleep(true)`.
4. Thread-2 writes `scout.asleep` while Thread-1 can perform the conflicting read.

**Why this produces the JPF symptom:**

Both threads operate on the same shared `CountingFireflies` object. Thread-1 reads `asleep`, while Thread-2 writes the same field. In the original program, these accesses are not protected by a common lock, so `PreciseRaceDetector` reports a race on `CountingFireflies.asleep`.

## 4. Suggested solution

**Fix type**

* [x] Add or widen synchronization (synchronized / lock)
* [ ] Use an atomic or concurrent class
* [ ] Add volatile
* [ ] Change lock order / lock granularity
* [ ] Fix wait/notify (condition loop, notifyAll, missing signal)
* [ ] Thread confinement or immutability
* [ ] Other: n/a

**Where to apply it** *(file:line range)*:

`CountingFireflies.java:5` and `CountingFireflies.java:20`, protecting both accesses to `asleep` with the same lock.

**Description of the fix:**

Introduce a dedicated `asleepLock` object and synchronize both the read of `asleep` in `tryToSleep()` and the write of `asleep` in `setAsleep()` on that same lock. The lock is held only around the individual field access so that Thread-2 remains able to acquire the lock and update the state.

**Code sketch**

```java
// before

private volatile boolean asleep = false;

public void tryToSleep() {
    while (!asleep) {
        countSomeSheep();
    }
}

public void setAsleep(boolean value) {
    this.asleep = value;
}
```

```java
// after

private boolean asleep = false;
private final Object asleepLock = new Object();

public void tryToSleep() {
    while (true) {
        boolean isAsleep;

        synchronized (asleepLock) {
            isAsleep = asleep;
        }

        if (isAsleep) {
            break;
        }

        countSomeSheep();
    }
}

public void setAsleep(boolean value) {
    synchronized (asleepLock) {
        this.asleep = value;
    }
}
```

**Why it removes the interleaving:**

The read and write of `asleep` now both require the same `asleepLock`. Therefore, the protected read and write cannot execute concurrently. This removes the conflicting interleaving that triggered the JPF `PreciseRaceDetector` report, and the modified program passes JPF.

**Other acceptable fixes** *(there is often more than one)*:

A `java.util.concurrent.locks.Lock` can be used instead of `synchronized`, provided the same lock protects both accesses. A correctly synchronized condition-based design using `wait()/notifyAll()` or `Condition` can also replace the polling design.

**Invalid or superficial fixes for this bug** *(e.g. fewer threads, smaller workload, sleep, removed concurrency, one global lock):*

* Adding or increasing `Thread.sleep(...)` does not synchronize the accesses.
* Changing timing or workload does not correct the shared-state access.
* Removing one of the threads removes concurrency instead of fixing the underlying defect.
* Making the entire `tryToSleep()` method synchronized is unsuitable here because Thread-1 can hold the monitor while looping, preventing Thread-2 from acquiring it to set `asleep = true`.
* Adding `volatile` alone is not considered the fix for this JPF-reported case, since the race was observed with and without `volatile`.
