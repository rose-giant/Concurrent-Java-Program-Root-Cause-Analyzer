## 3. Root cause

**Shared state** *(variable / object / lock):*

n/a as a concurrency bug.

The real shared state is the `ConcurrentHashMap` inside `DelegatingVehicleTracker`. The failing reference is the captured local `tracker` inside the lambda executed by a pool worker.

**Accesses involved**

| Thread       | Method               | Line | Operation (R/W/lock/wait/notify)              |
| ------------ | -------------------- | ---- | --------------------------------------------- |
| pool worker  | `Main.lambda$main$0` | 1    | Method invocation on null `tracker` reference |
| n/a          | n/a                  | n/a  | n/a                                           |

**Guarantee that is missing** *(what should be atomic, ordered, or protected):*

None at the program level. `ConcurrentHashMap.replace` is atomic, `Point` is immutable, and `getLocationsAsStatic()` copies from a thread-safe map. `ExecutorService.execute` gives a happens-before edge from submission to execution, so `tracker` is safely visible to the workers. `setLocation("1", ...)` targets a key that exists, so no `IllegalArgumentException` is expected. The missing guarantee is in the tool's handling of lambda capture.

**Buggy interleaving** *(2 to 4 steps)*

n/a. The failure is not caused by a concurrency interleaving between conflicting shared accesses.

**Why this produces the JPF symptom:**

In the source program, `tracker` is initialized with:

```java
DelegatingVehicleTracker tracker = new DelegatingVehicleTracker(initial);
```

and is never assigned `null`. Nevertheless, JPF reports that the receiver of `setLocation()` in `Main.lambda$main$0` is null.

A lambda capturing the local `tracker` compiles to `invokedynamic`, and JPF synthesizes a `Main$$Lambda$0` class to carry the captured value. The null receiver inside the synthetic body suggests the captured value was not propagated correctly. The fix supports this: making `tracker` a static field, so that the lambdas capture nothing and read it with `getstatic`, removes the error while the lambdas and the executor stay exactly as they were. The exact JPF mechanism was not verified.

The executor is not involved in the failure. JPF ran `ThreadPoolExecutor.runWorker` normally up to the lambda, and the fixed version keeps the executor.

## 4. Suggested solution

**Fix type**

* [ ] Add or widen synchronization (synchronized / lock)
* [ ] Use an atomic or concurrent class
* [ ] Add volatile
* [ ] Change lock order / lock granularity
* [ ] Fix wait/notify (condition loop, notifyAll, missing signal)
* [ ] Thread confinement or immutability
* [x] Other: **Make the captured local a static field so the lambdas capture nothing**

**Where to apply it** *(file:line range)*:

`Main` class and `Main.main`: add `static DelegatingVehicleTracker tracker;` as a field and change the local declaration in `main` to a plain assignment. The old source is on a single line, so line ranges are not meaningful. The lambdas, the executor, `Point` and `DelegatingVehicleTracker` are unchanged.

**Description of the fix:**

Move `tracker` from a local variable of `main` to a `static` field of `Main`. The lambdas then read the static field instead of capturing a local, so no captured argument has to be passed into the synthetic lambda class.

**Code sketch**

```java
// before

public class Main {
    public static void main(String[] args) throws Exception {
        // ...
        DelegatingVehicleTracker tracker = new DelegatingVehicleTracker(initial);
        ExecutorService es = Executors.newFixedThreadPool(2);
        es.execute(() -> { tracker.setLocation(String.valueOf(1), 1, 1); });
        es.execute(() -> { tracker.getLocationsAsStatic(); });
        // ...
    }
}
```

```java
// after

public class Main {
    static DelegatingVehicleTracker tracker;

    public static void main(String[] args) throws Exception {
        // ...
        tracker = new DelegatingVehicleTracker(initial);
        ExecutorService es = Executors.newFixedThreadPool(2);
        es.execute(() -> { tracker.setLocation(String.valueOf(1), 1, 1); });
        es.execute(() -> { tracker.getLocationsAsStatic(); });
        // ...
    }
}
```

**Why it removes the symptom:**

n/a as an interleaving fix. The lambdas no longer capture a local variable, so the code path that appears to lose the captured value is not used. Visibility is not a concern: the assignment happens before `execute`, which gives a happens-before edge to the workers.

**Validation:**

The supplied fixed version (local → static field, nothing else changed) is taken as passing JPF per the case record. This was not re-run here.
