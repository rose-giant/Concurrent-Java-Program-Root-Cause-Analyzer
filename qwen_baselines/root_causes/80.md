**Shared state** *(variable / object / lock):*

The source is on a single line, so line numbers are not meaningful. These accesses are not related to the failure.

**Guarantee that is missing** *(what should be atomic, ordered, or protected):*

None at the program level. This is the standard immutable-holder-plus-`volatile` idiom: `OneValueCache` has only `final` fields and defensive array copies, so any thread that reads `cache` sees a consistent number/factors pair. `service` does check-then-act (read, miss, write), so two threads can both miss and both write. This is benign here because each result is correct on its own and there is no invariant that spans calls. It is not the cause of the reported failure.

**Why this produces the JPF symptom:**

The root cause is not determined by the supplied evidence. The failure is an abnormal termination inside JPF, not a violation found in the program.

The most likely trigger is the use of `ExecutorService` (`Executors.newFixedThreadPool`, `execute`, `shutdown`, `awaitTermination(1, TimeUnit.SECONDS)`). It pulls in `ThreadPoolExecutor`, worker threads, a blocking queue, AQS-based locking and a timed wait, and JPF models parts of this only partially.

## 4. Suggested solution

**Fix type**

* [ ] Add or widen synchronization (synchronized / lock)
* [ ] Use an atomic or concurrent class
* [ ] Add volatile
* [ ] Change lock order / lock granularity
* [ ] Fix wait/notify (condition loop, notifyAll, missing signal)
* [ ] Thread confinement or immutability
* [x] Other: **Avoid `ExecutorService`; use plain `Thread`s with `start()` and `join()`**

**Where to apply it** *(file:line range)*:

`Main.main`. The old source is on a single line, so line ranges are not meaningful. `OneValueCache` and `Factorizer` need no change for the fix.

**Description of the fix:**

Replace the fixed thread pool and its two `execute(...)` calls with two `Thread`s (the existing lambdas can be reused), start them, and `join()` both. Remove `shutdown()`, `awaitTermination(...)` and the `java.util.concurrent` import.

The supplied fixed version also declares `Factorizer.service` as `synchronized`. This is not needed to fix the failure. The `volatile` + immutable holder design was already thread-safe, and the extra lock only serializes calls. A version without it is the truly minimal fix, but it was not tested.

**Code sketch**

```java
// before

ExecutorService es = Executors.newFixedThreadPool(2);
es.execute(() -> { factorizer.service(BigInteger.ONE); });
es.execute(() -> { factorizer.service(BigInteger.valueOf(2)); });
es.shutdown();
es.awaitTermination(1, TimeUnit.SECONDS);
```

```java
// after

Thread t1 = new Thread(() -> { factorizer.service(BigInteger.ONE); });
Thread t2 = new Thread(() -> { factorizer.service(BigInteger.valueOf(2)); });
t1.start();
t2.start();
t1.join();
t2.join();
```

**Why it removes the symptom:**

n/a as an interleaving fix. The new program uses only `Thread`, `volatile`, `synchronized` and `join`, which JPF supports natively, and it no longer touches the thread-pool classes.

**Validation:**

The supplied fixed version (executor → plain threads, lambdas kept, `service` made `synchronized`) is taken as passing JPF per the case record. This was not re-run here.

**Behavioral note:**

The old code waited at most 1 second and ignored the result of `awaitTermination`. The new code waits for both threads to finish. This does not affect the correctness of the logic.

**Other acceptable fixes** *(there is often more than one)*:

Plain threads with anonymous `Runnable` classes instead of lambdas. This should also work, but it is not needed here, since the lambdas passed.

**Invalid or superficial fixes for this bug:**

* Adding `synchronized` to `service` while keeping the executor
* Adding or removing `volatile` on `cache`
* Adding `Thread.sleep()`
* Changing the pool size or executor type (these still use the thread-pool machinery)
