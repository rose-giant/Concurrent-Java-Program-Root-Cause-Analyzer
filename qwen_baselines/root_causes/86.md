  * `pool-1-thread-2` at `PublishingVehicleTracker.getLocation`: `READ: getfield SafePoint.x`

* **Counterexample summary (threads, key steps):**

  1. `main()` creates a tracker holding one `SafePoint(0, 0)` under key `"1"` and a fixed pool of 2 threads, then submits two lambda tasks.
  2. `pool-1-thread-1` runs `setLocation("1", 2, 2)`. It looks up the `SafePoint` `p` and executes `p.x = x`.
  3. `pool-1-thread-2` runs `getLocation("1")`. It looks up the same `SafePoint` and executes `p.x` (and then `p.y`) to build a copy.
  4. The two methods hold no common lock, so JPF reports the conflicting accesses to `SafePoint.x` as a race.
  5. The search stopped at the first error after 6105 new states, at search depth 3000 (equal to the `max_depth` in the log, so likely the configured limit), with 3 logical threads.

## 3. Root cause

**Shared state** *(variable / object / lock):*

The mutable `SafePoint` object stored in the map: its fields `x` and `y`. The invariant is that the pair `(x, y)` always represents one location.

**Accesses involved**

| Thread          | Method                                  | Line | Operation (R/W/lock/wait/notify)            |
| --------------- | --------------------------------------- | ---- | ------------------------------------------- |
| pool-1-thread-1 | `PublishingVehicleTracker.setLocation`  | 1    | W `p.x`, then W `p.y` (no lock)             |
| pool-1-thread-2 | `PublishingVehicleTracker.getLocation`  | 1    | R `p.x`, then R `p.y` (no lock)             |

**Guarantee that is missing** *(what should be atomic, ordered, or protected):*

The update of `(x, y)` in `setLocation` and the read of `(x, y)` in `getLocation` must be atomic with respect to each other. `volatile` makes each field's access individually visible and ordered, but it does not make the two-field update or the two-field read atomic.

**Buggy interleaving** *(2 to 4 steps)*

1. `pool-1-thread-1` executes `p.x = 2` (`p` is still `(0, 0)`, now `(2, 0)`).
2. `pool-1-thread-2` executes `getLocation`: it reads `p.x = 2` and `p.y = 0`.
3. `pool-1-thread-1` executes `p.y = 2`.

Result: the reader returns `(2, 0)`, a location that was never set (only `(0, 0)` and `(2, 2)` ever existed). This interleaving was derived by analysis; JPF's report does not show it.

**Why this produces the JPF symptom:**

`setLocation` writes `SafePoint.x` while `getLocation` reads it, in different threads and with no common lock. JPF's `PreciseRaceDetector` flags this conflicting pair. The `volatile` modifier does not stop the report, which suggests that this detector does not treat `volatile` accesses as synchronized. That is inferred from this report; the detector's internals were not inspected.

## 4. Suggested solution

**Fix type**

* [x] Add or widen synchronization (synchronized / lock)
* [ ] Use an atomic or concurrent class
* [ ] Add volatile
* [ ] Change lock order / lock granularity
* [ ] Fix wait/notify (condition loop, notifyAll, missing signal)
* [ ] Thread confinement or immutability
* [ ] Other

**Where to apply it** *(file:line range)*:

`PublishingVehicleTracker.getLocation` and `PublishingVehicleTracker.setLocation`. The source is on a single line, so line ranges are not meaningful.

**Description of the fix:**

Declare both `getLocation` and `setLocation` as `synchronized`, so that the two-field write and the two-field read hold the same monitor (the tracker) and cannot interleave. `SafePoint` and `main` are unchanged. The `volatile` modifiers on `x` and `y` are kept. They are no longer needed by these two methods, but they still give visibility to any unsynchronized reader.

**Code sketch**

```java
// before

SafePoint getLocation(String id) {
    SafePoint p = locations.get(id);
    return p == null ? null : new SafePoint(p.x, p.y);
}

void setLocation(String id, int x, int y) {
    SafePoint p = locations.get(id);
    if (p == null) throw new IllegalArgumentException();
    p.x = x;
    p.y = y;
}
```

```java
// after

synchronized SafePoint getLocation(String id) {
    SafePoint p = locations.get(id);
    return p == null ? null : new SafePoint(p.x, p.y);
}

synchronized void setLocation(String id, int x, int y) {
    SafePoint p = locations.get(id);
    if (p == null) throw new IllegalArgumentException();
    p.x = x;
    p.y = y;
}
```

**Why it removes the interleaving:**

Both methods now hold the tracker's monitor while they touch `p.x` and `p.y`. The reader can no longer run between the two writes, and JPF sees a common lock on the conflicting accesses.

**Validation:**

The supplied fixed version is taken as passing JPF per the case record. This was not re-run here.

**Other acceptable fixes** *(there is often more than one)*:

* Synchronize on the `SafePoint` itself (`synchronized (p) { ... }` in both methods, or synchronized accessors in `SafePoint`).
* Make `SafePoint` immutable and replace it atomically, as in `DelegatingVehicleTracker`: `locations.replace(id, new SafePoint(x, y))`. This is lock-free but changes the design.

Neither was tested.

**Invalid or superficial fixes for this bug:**

* Adding `volatile` (the fields already are `volatile`)
* Synchronizing only `setLocation` or only `getLocation`
* Replacing `x` and `y` with two separate `AtomicInteger`s (each field is atomic, the pair is not)
* Changing the `ConcurrentHashMap`
* Adding `Thread.sleep()`
* Reducing the number of threads

None of these makes the pair `(x, y)` atomic.
