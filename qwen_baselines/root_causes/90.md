* **Counterexample summary (threads, key steps):**

  1. `main()` creates a fixed pool of 1 thread and submits a `PrimeGenerator`.
  2. `pool-1-thread-1` runs `run()`, whose loop reads `cancelled` through `while (!cancelled && ...)`.
  3. `main` sleeps, then calls `cancel()`, which executes `cancelled = true`.
  4. The write in `main` and the read in the pool thread hold no common lock, so JPF reports a race on `cancelled`.
  5. The search stopped at the first error after 717 new states, at search depth 55, with 2 logical threads.

## 3. Root cause

**Shared state** *(variable / object / lock):*

`PrimeGenerator.cancelled`, a `volatile boolean` used as a cancellation flag. The list `primes` is a `Collections.synchronizedList` and is not part of the report.

**Accesses involved**

| Thread          | Method                    | Line | Operation (R/W/lock/wait/notify)       |
| --------------- | ------------------------- | ---- | -------------------------------------- |
| main            | `PrimeGenerator.cancel`   | 1    | W `cancelled` (volatile)               |
| pool-1-thread-1 | `PrimeGenerator.run`      | 1    | R `cancelled` (volatile), in the loop  |

**Guarantee that is missing** *(what should be atomic, ordered, or protected):*

None. This is the standard `volatile` cancellation-flag idiom. A single independent boolean needs only visibility and ordering, which `volatile` provides, and there is no compound action across fields. The worker is guaranteed to see the write eventually, and it also stops after one second on its own. The `volatile` accesses are synchronization actions, so no data race exists under the JMM.

**Buggy interleaving** *(2 to 4 steps)*

n/a. No interleaving of the write and the read produces an incorrect result.

**Why this produces the JPF symptom:**

`PreciseRaceDetector` reports two conflicting accesses to the same field in different threads without a common lock. The `volatile` modifier does not stop the report, which indicates that this detector does not treat `volatile` accesses as synchronization. This is an inference from this report and from Vehicle-Tracker-P86, which showed the same behavior; the detector's internals were not inspected.

## 4. Suggested solution

**Fix type**

* [x] Add or widen synchronization (synchronized / lock)
* [ ] Use an atomic or concurrent class
* [ ] Add volatile
* [ ] Change lock order / lock granularity
* [ ] Fix wait/notify (condition loop, notifyAll, missing signal)
* [ ] Thread confinement or immutability
* [ ] Other

The synchronization is not required for correctness. It is added so that both accesses hold a common lock and the detector no longer reports them.

**Where to apply it** *(file:line range)*:

`PrimeGenerator`: the `cancel()` method, a new `isCancelled()` method, and the loop condition in `run()`. The source is on a single line, so line ranges are not meaningful.

**Description of the fix:**

Add a `synchronized boolean isCancelled()` that returns `cancelled`, make `cancel()` `synchronized`, and change the loop in `run()` from `!cancelled` to `!isCancelled()`. Now the write and the read both happen while holding the `PrimeGenerator` monitor. The `volatile` modifier is kept. It is redundant but harmless.

**Code sketch**

```java
// before

while (!cancelled && System.currentTimeMillis() < end) { ... }

void cancel() { cancelled = true; }
```

```java
// after

while (!isCancelled() && System.currentTimeMillis() < end) { ... }

synchronized boolean isCancelled() { return cancelled; }
synchronized void cancel() { cancelled = true; }
```

**Why it removes the symptom:**

The conflicting accesses to `cancelled` now both hold the same monitor, so JPF sees a common lock and no longer reports a race. The program's behavior is unchanged.

**Validation:**

The supplied fixed version is taken as passing JPF per the case record. This was not re-run here.

**Other acceptable fixes** *(there is often more than one)*:

* Replace the flag with an `AtomicBoolean`.
* Cancel through `Future.cancel(true)` and thread interruption.

Neither was tested against the detector, so it is not known whether it would stay quiet.

**Invalid or superficial fixes for this bug:**

* Adding `volatile` (the field already is `volatile`)
* Removing `volatile` while leaving the accesses unsynchronized (this would create a real data race)
* Replacing the executor with plain threads (the same two accesses remain)
* Changing the pool size, the `Thread.sleep` duration or the 1-second deadline
* Changing the `primes` list

None of these removes the reported conflict.
