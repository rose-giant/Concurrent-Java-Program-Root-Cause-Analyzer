**Why this produces the JPF symptom (hypothesis, unconfirmed):**

1. The driver uses `Executors.newFixedThreadPool(3)` and a timed `awaitTermination(1, SECONDS)`. These pull in `ThreadPoolExecutor`, `LinkedBlockingQueue`, AQS and timed waits, which JPF models poorly.
2. The workload is large for model checking: 3 threads, each doing 5 push and 5 pop. Every CAS retry and every `System.out.print` is a scheduling point, so the interleavings explode and the search probably hits `max_depth` 3000.

## 4. Suggested solution

**Fix type**

* [ ] Add or widen synchronization
* [ ] Use an atomic or concurrent class
* [ ] Add volatile
* [ ] Change lock order / lock granularity
* [ ] Fix wait/notify
* [ ] Thread confinement or immutability

**Where to apply it:** `Main.main()`. `ConcurrentStack` stays unchanged.

**Description of the fix:** Replace the executor with plain `Thread` objects and `join()` them, and reduce the workload to 2 threads x 2 iterations. Remove `System.out.print` if the search still does not terminate. This is a workaround for JPF's limits, not a concurrency fix.

**Code sketch**

```java
// before
ExecutorService es = Executors.newFixedThreadPool(3);
for (int i = 0; i < 3; i++) {
    es.execute(() -> {
        for (int j = 0; j < 5; j++) { stack.push(j); System.out.print('P'); }
        for (int j = 0; j < 5; j++) { stack.pop();  System.out.print('O'); }
    });
}
es.shutdown();
es.awaitTermination(1, TimeUnit.SECONDS);
System.out.print('C');
```

```java
// after
Runnable task = () -> {
    for (int j = 0; j < 2; j++) { stack.push(j); System.out.print('P'); }
    for (int j = 0; j < 2; j++) { stack.pop();  System.out.print('O'); }
};
Thread t1 = new Thread(task);
Thread t2 = new Thread(task);
t1.start(); t2.start();
t1.join(); t2.join();
System.out.print('C');
```

**Why it removes the symptom:** Plain threads avoid the `ThreadPoolExecutor` and timed-wait machinery. The smaller workload shrinks the state space so the search can finish within depth 3000. It does not change any shared-state access, because the stack was already correct.

**Other acceptable fixes:**

* Keep the executor but swap `awaitTermination(1, SECONDS)` for an untimed `awaitTermination(Long.MAX_VALUE, ...)`, or raise JPF's `search.depth_limit`.
* Remove the `System.out.print` calls.
* Add a JPF partial-order-reduction or listener config instead of editing the code.

**Invalid or superficial fixes for this case:**

* Treating the changes above as a repair of a concurrency bug. They only change the test driver, and the original program has no bug.
* Adding locks around `push` and `pop`, which would change the algorithm for no reason.
* Adding `volatile` or `synchronized` to the stack. It is already correct.
