## 3. Root cause

**Shared state** *(variable / object / lock):*

`CountingComets.asleep`, a mutable field of the single shared `CountingComets` instance `wanderer`.

**Accesses involved**

| Thread   | Method               | Line | Operation (R/W/lock/wait/notify) |
| -------- | -------------------- | ---- | -------------------------------- |
| Thread-1 | `tryToSleep()`       | 5    | R (`while (!asleep)`)            |
| Thread-2 | `setAsleep(boolean)` | 20   | W (`this.asleep = value`)        |

**Guarantee that is missing** *(what should be atomic, ordered, or protected):*

The conflicting read and write of the shared variable `asleep` must be protected by a common synchronization mechanism so that the accesses cannot occur concurrently under JPF's race-detection model.

**Buggy interleaving** *(2 to 4 steps)*

1. Thread-1 reads `wanderer.asleep` while executing `while (!asleep)`.
2. Thread-1 remains active and continues checking the shared field.
3. Thread-2 finishes its delay and calls `wanderer.setAsleep(true)`.
4. Thread-2 writes `wanderer.asleep` while Thread-1 can perform the conflicting read.

**Why this produces the JPF symptom:**

Both threads operate on the same shared `CountingComets` object. Thread-1 reads `asleep`, while Thread-2 writes the same field. The original code does not protect these accesses with a common lock, so JPF's `PreciseRaceDetector` reports a race on `CountingComets.asleep`.

## 4. Suggested solution

**Fix type**

* [x] Add or widen synchronization (synchronized / lock)
* [ ] Use an atomic or concurrent class
* [ ] Add volatile
* [ ] Change lock order / lock granularity
* [ ] Fix wait/notify (condition loop, notifyAll, missing signal)
* [ ] Thread confinement or immutability
* [ ] Other: n/a

**Where to apply it** *(file:line range)*:

`CountingComets.java:5` and `CountingComets.java:20`, protecting both accesses to `asleep` with the same lock.

**Description of the fix:**

Replace the unsynchronized access to `asleep` with a dedicated `asleepLock`. The read in `tryToSleep()` and the write in `setAsleep()` are both enclosed in `synchronized (asleepLock)` blocks. The lock is held only during the individual field access rather than for the entire `tryToSleep()` loop.

**Code sketch**

```java
// before

private volatile boolean asleep = false;

public void tryToSleep() {
    while (!asleep) {
        countSomeSheep();
    }
}

public void setAsleep(boolean value) {
    this.asleep = value;
}
```

```java
// after

private boolean asleep = false;
private final Object asleepLock = new Object();

public void tryToSleep() {
    while (true) {
        boolean isAsleep;

        synchronized (asleepLock) {
            isAsleep = asleep;
        }

        if (isAsleep) {
            break;
        }

        countSomeSheep();
    }
}

public void setAsleep(boolean value) {
    synchronized (asleepLock) {
        this.asleep = value;
    }
}
```

**Why it removes the interleaving:**

The read and write now require ownership of the same `asleepLock`. Consequently, Thread-1 cannot perform the protected read at the same time that Thread-2 performs the protected write. The conflicting access pair reported by JPF is therefore eliminated. The modified program was confirmed to pass JPF.

**Other acceptable fixes** *(there is often more than one):*

Equivalent mutual-exclusion using `java.util.concurrent.locks.Lock` is acceptable, provided the same lock protects both accesses. A properly synchronized condition-based design using `wait()/notifyAll()` or `Condition` could also be used as a redesign.

**Invalid or superficial fixes for this bug** *(e.g. fewer threads, smaller workload, sleep, removed concurrency, one global lock):*

* Adding or increasing `Thread.sleep(...)` does not provide synchronization.
* Changing the timing or reducing the workload does not fix the shared-state access.
* Removing a thread removes the concurrent execution rather than correcting the underlying defect.
* Making the entire `tryToSleep()` method synchronized is unsuitable here because Thread-1 can retain the monitor while looping, preventing Thread-2 from acquiring the same monitor to update `asleep`.
* Adding `volatile` alone is not considered the reference fix for this JPF-reported case, since the original experiment produced the race report both with and without `volatile`.
