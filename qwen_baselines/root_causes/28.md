* **Location (file:line):**

  `Main.java:33` (call site), failing inside `java.util.Comparator.comparing(Comparator.java:468)`

  ```java
  Collections.sort(localRunes, Comparator.comparing((Rune r) -> r.constellation).thenComparing(r -> r.resonance));
  ```

* **Counterexample summary (threads, key steps):**

  1. `main()` builds a 4-element `candidates` list and starts `t1` and `t2`, each running a lambda that calls `channelTheGrimoire(candidates)`.
  2. `t1` enters `channelTheGrimoire` (`Main.java:14`), copies the list into `localRunes`, and evaluates `Comparator.comparing(...)` at line 33.
  3. Inside the JDK's `Comparator.comparing`, JPF fails a cast of the synthetic lambda class `Comparator$$Lambda$2` to `java.io.Serializable`.
  4. The exception is uncaught in `t1`. It occurs at search depth 7, before any interleaving choice matters, and the search stops at the first error.

## 3. Root cause

**Shared state** *(variable / object / lock):*

n/a as a concurrency bug.

The only object shared by both threads is `candidates`, which is not modified after the threads start and is only read (copied) by each thread. `Rune` is immutable. `localRunes` and `grimoire` are created per invocation, so they are thread-confined.

**Accesses involved**

| Thread | Method                                         | Line | Operation (R/W/lock/wait/notify)                                   |
| ------ | ---------------------------------------------- | ---- | ------------------------------------------------------------------ |
| `t1`   | `java.util.Comparator.comparing` (JDK)         | 468  | Cast of synthetic lambda class to `Serializable` fails (`checkcast`) |
| n/a    | n/a                                            | n/a  | n/a                                                                |

**Guarantee that is missing** *(what should be atomic, ordered, or protected):*

None at the program level. The program is correctly thread-confined and the shared `candidates` list is effectively read-only. The missing guarantee is in the tool: JPF's synthetic lambda class does not implement the marker interface that the JDK's own code casts to.

**Buggy interleaving** *(2 to 4 steps)*

n/a. The failure is not caused by a concurrency interleaving between conflicting shared accesses.

**Why this produces the JPF symptom:**

The cast is not in the application code. In the JDK, `Comparator.comparing` returns a lambda declared with an intersection cast, `(Comparator<T> & Serializable)`. The compiler implements this through `LambdaMetafactory.altMetafactory` with the serializable marker. JPF synthesizes a class `Comparator$$Lambda$2` for the lambda, and that class evidently does not implement `Serializable`, so the resulting `checkcast` throws `ClassCastException`. This is an inference from the stack trace and from the fix. The exact JPF mechanism was not verified.

The lambdas in `main` (which capture `candidates`) run without error under JPF in the fixed version. So the failing construct is the JDK's serializable comparator lambda, not lambdas in general.

There is no evidence in the supplied source of an application-level defect.

## 4. Suggested solution

**Fix type**

* [ ] Add or widen synchronization (synchronized / lock)
* [ ] Use an atomic or concurrent class
* [ ] Add volatile
* [ ] Change lock order / lock granularity
* [ ] Fix wait/notify (condition loop, notifyAll, missing signal)
* [ ] Thread confinement or immutability
* [x] Other: **Avoid `Comparator.comparing` / `thenComparing`; use an explicit `Comparator` implementation**

**Where to apply it** *(file:line range)*:

`Main.java:33`, the `Collections.sort(...)` call in `channelTheGrimoire`. The lambdas in `main` (lines 13-16 and 17-20) do not need to change.

**Description of the fix:**

Replace the `Comparator.comparing((Rune r) -> r.constellation).thenComparing(r -> r.resonance)` chain with an anonymous `Comparator<Rune>` that compares `constellation` first and then `resonance` using `compareTo`. This gives the same ordering and never enters the JDK's serializable-lambda code path.

**Code sketch**

```java
// before

Collections.sort(localRunes, Comparator.comparing((Rune r) -> r.constellation).thenComparing(r -> r.resonance));
```

```java
// after

Collections.sort(localRunes, new Comparator<Rune>() {
    @Override
    public int compare(Rune a, Rune b) {
        int result = a.constellation.compareTo(b.constellation);
        if (result != 0) {
            return result;
        }
        return a.resonance.compareTo(b.resonance);
    }
});
```

**Why it removes the symptom:**

n/a as an interleaving fix. The anonymous class is an ordinary class, so no `invokedynamic` or `altMetafactory` call is involved and no serializable-lambda cast occurs.

**Validation:**

Fix applied (comparator chain → explicit `Comparator`, no change to sort order or program logic): the reported `ClassCastException` no longer occurs and the run passes JPF. The `main` lambdas were left as they were and did not fail.

**Other acceptable fixes** *(there is often more than one)*:

* A named class implementing `Comparator<Rune>`.
* A plain lambda comparator such as `(a, b) -> ...` passed to `Collections.sort`. This avoids `Comparator.comparing`'s serializable cast and should work, since the `main` lambdas do, but it was not tested.

**Invalid or superficial fixes for this bug:**

* Adding synchronization around `channelTheGrimoire` or `candidates`
* Wrapping `candidates` in `Collections.synchronizedList`
* Adding `volatile` to anything
* Adding `Thread.sleep()`
* Running only one thread
* Changing `Grimoire` or `Harmony`
* Using a different `Comparator.comparing` overload or method references (they go through the same JDK method)
* Replacing the lambdas in `main` (they are not the failing construct)

None of these addresses the reported cast failure.
