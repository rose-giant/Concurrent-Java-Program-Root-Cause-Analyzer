## 3. Root cause

**Shared state:** `Sleeper.asleep`, a mutable boolean field of the single shared `Sleeper` instance `sleeper`. In the original it is declared `volatile`.

**Accesses involved**

| Thread          | Method                | Line        | Operation (R/W/lock/wait/notify)      |
| --------------- | --------------------- | ----------- | ------------------------------------- |
| pool-1-thread-1 | `tryToSleep()`        | Main.java:1 | R (`while (!asleep)`)                 |
| pool-1-thread-2 | `Main.lambda$main$1`  | Main.java:1 | W (`sleeper.asleep = true`)           |

**Guarantee that is missing:** the read and write of `asleep` should be protected by a common synchronization mechanism, according to JPF's race-detection model. Declaring the field `volatile` does not satisfy `PreciseRaceDetector`.

**Buggy interleaving**

1. pool-1-thread-1 starts `tryToSleep()` and reads `asleep` (false).
2. pool-1-thread-1 sleeps 1 ms and loops, reading `asleep` again each time.
3. pool-1-thread-2 finishes `Thread.sleep(10)` and executes `sleeper.asleep = true`.
4. The write and the reads touch the same field with no common lock.

**Why this produces the JPF symptom:**

`sleeper` is shared by both tasks. One thread reads `asleep` and the other writes it with no common lock, so `PreciseRaceDetector` reports a race even though the field is `volatile`. Under the Java memory model this volatile flag is not a data race. The report is JPF's, and the benchmark follows it.

## 4. Suggested solution

**Fix type**

* [x] Add or widen synchronization (synchronized / lock)
* [ ] Use an atomic or concurrent class
* [ ] Add volatile
* [ ] Change lock order / lock granularity
* [ ] Fix wait/notify
* [ ] Thread confinement or immutability
* [ ] Other: n/a

**Where to apply it:** the `asleep` field declaration, the loop condition in `Sleeper.tryToSleep()`, two new accessor methods in `Sleeper`, and the write in the second lambda of `Main.main`.

**Description of the fix:** make `asleep` a plain private field guarded by the monitor of `this`, and access it only through short synchronized accessors. `tryToSleep()` reads it through `isAsleep()`, and `Main` writes it through `setAsleep(true)`. Each lock is held only for the single field access, so the polling thread releases the monitor between iterations and the writer can always acquire it.

**Code sketch**

```java
// before
volatile boolean asleep;

void tryToSleep() {
    while (!asleep) countSomeSheep();
}

// in Main.main, second task
sleeper.asleep = true;
```

```java
// after
private boolean asleep;   // guarded by "this"

synchronized boolean isAsleep()         { return asleep; }
synchronized void setAsleep(boolean v)  { asleep = v; }

void tryToSleep() {
    while (!isAsleep()) countSomeSheep();
}

// in Main.main, second task
sleeper.setAsleep(true);
```

**Why it removes the interleaving:** both the read and the write of `asleep` now require the same monitor, so they cannot overlap and JPF sees a common lock for the field.

**Other acceptable fixes:**

* A dedicated private lock object instead of `this`, with the same short scoping.
* `ReentrantLock` guarding the two accesses.
* A `wait()`/`notifyAll()` redesign, where `tryToSleep()` waits in a condition loop instead of polling and the writer sets the flag and calls `notifyAll()`. This also removes the busy-wait that drives the search to maxDepth, but it is a larger change.
* `AtomicBoolean` is plausible but unverified under JPF's detector. Test before accepting it.

**Invalid or superficial fixes for this bug:**

* Keeping `volatile`. The original already has it, and JPF still reports the race.
* Making `tryToSleep()` a `synchronized` method. `Thread.sleep` does not release the monitor, so the polling thread would hold it almost permanently and the writer could never set the flag.
* Changing the `Thread.sleep(...)` durations or reducing the iterations.
* Removing a thread or the executor, which removes the concurrency.
* Replacing the program with a different one (for example an `IntHolder` with synchronized `get`/`set`), which does not repair this code.
