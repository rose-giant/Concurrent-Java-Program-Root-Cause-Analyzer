## 3. Root cause

**Shared state:** `PrimeGenerator.cancelled`, a mutable boolean field of the single shared `PrimeGenerator` instance. In the original it is declared `volatile`.

**Accesses involved**

| Thread        | Method     | Line      | Operation (R/W/lock/wait/notify)       |
| ------------- | ---------- | --------- | -------------------------------------- |
| pool-1-thread-1 | `run()`  | Main.java:1 | R (`while (!cancelled && ...)`)      |
| main          | `cancel()` | Main.java:1 | W (`cancelled = true`)               |

**Guarantee that is missing:** the read and write of `cancelled` are not protected by a common synchronization mechanism, according to JPF's race-detection model. Declaring the field `volatile` does not satisfy `PreciseRaceDetector`.

**Buggy interleaving**

1. main calls `generator.start()`, and pool-1-thread-1 starts `run()` and reads `cancelled` (false).
2. pool-1-thread-1 keeps looping, reading `cancelled` on each iteration.
3. main finishes `Thread.sleep(1000)` and calls `cancel()`, which writes `cancelled = true`.
4. The write by main and the read by pool-1-thread-1 touch the same field with no common lock.

**Why this produces the JPF symptom:**

`PreciseRaceDetector` reports two accesses by different threads to the same field without a common lock, even when the field is `volatile`. Under the Java memory model, a `volatile` flag read and written like this is not a data race. The report is JPF's, and the benchmark follows it.

## 4. Suggested solution

**Fix type**

* [x] Add or widen synchronization (synchronized / lock)
* [ ] Use an atomic or concurrent class
* [ ] Add volatile
* [ ] Change lock order / lock granularity
* [ ] Fix wait/notify
* [ ] Thread confinement or immutability
* [ ] Other: n/a

**Where to apply it:** the field declaration, the loop condition in `run()`, and `cancel()`.

**Description of the fix:** make `cancelled` a plain field guarded by the monitor of `this`, and access it only through short synchronized accessors, `isCancelled()` and `setCancelled()`. `run()` calls `isCancelled()` in its loop condition and `cancel()` calls `setCancelled()`. Each lock is held only for the single field access, so the worker releases the monitor between iterations and main can always acquire it.

**Code sketch**

```java
// before
private volatile boolean cancelled;

public void run() {
    ...
    while (!cancelled && primes.size() < 10 && System.currentTimeMillis() < end) {
        current = current.nextProbablePrime();
        primes.add(current);
    }
}

void cancel() {
    cancelled = true;
    executor.shutdown();
}
```

```java
// after
private boolean cancelled;   // guarded by "this"

private synchronized boolean isCancelled() { return cancelled; }
private synchronized void setCancelled()    { cancelled = true; }

public void run() {
    ...
    while (!isCancelled() && primes.size() < 10 && System.currentTimeMillis() < end) {
        current = current.nextProbablePrime();
        primes.add(current);
    }
}

void cancel() {
    setCancelled();
    executor.shutdown();
}
```

**Why it removes the interleaving:** both the read and the write of `cancelled` now hold the same monitor, so they cannot overlap and JPF sees a common lock for the field. No other shared field is involved: `primes` is already a synchronized list.

**Other acceptable fixes:**

* A dedicated private lock object (`cancelLock`) instead of `this`, with the same short scoping.
* `java.util.concurrent.locks.Lock` or `ReentrantLock` guarding the two accesses.
* `AtomicBoolean` is a plausible alternative, but it relies on volatile and CAS internally and is unverified under JPF's detector. Test before accepting it.

**Invalid or superficial fixes for this bug:**

* Keeping or adding `volatile` alone. The original already has it, and JPF still reports the race.
* Making `run()` a `synchronized` method. The worker would hold the monitor for the whole loop, so `setCancelled()` would block until the loop ends.
* Adding or changing `Thread.sleep(...)` or the 1000 ms deadline.
* Removing the executor or the worker thread, which removes the concurrency instead of fixing the access.
* Using one global lock around everything, which is broader than needed.
