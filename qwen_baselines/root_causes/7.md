## 2. JPF evidence

* **Violated property / error message:**

  `gov.nasa.jpf.vm.NoUncaughtExceptionsProperty`

  `java.lang.NullPointerException: Calling 'updatePosition(Ljava/lang/String;Ljava/lang/String;)Z' on null object`

* **Location (file:line):**

  `Main.java:13`

  Specifically:

  ```java
  tracker.updatePosition("G1", "Room3");
  ```

* **Counterexample summary (threads, key steps):**

  1. `main()` creates a `DelegatingDeviceTracker` and assigns it to the local variable `tracker`.
  2. `main()` creates `t1` using a lambda that captures `tracker`.
  3. JPF enters `Main$$Lambda$0.run`, the synthetic class generated for `t1`'s lambda, which delegates to `Main.lambda$main$0`.
  4. The receiver of `updatePosition()` is null. This happens on the very first execution of `t1`'s body (search depth 5, 5 new states), before any interleaving choice matters.
  5. The search stops at the first error, so `t2`'s lambda (same construct) is never reached.

## 3. Root cause

**Shared state** *(variable / object / lock):*

n/a as a concurrency bug.

The immediate failing reference is the captured `tracker` reference inside the lambda executed by `t1`.

**Accesses involved**

| Thread | Method               | Line | Operation (R/W/lock/wait/notify)              |
| ------ | -------------------- | ---- | --------------------------------------------- |
| `t1`   | `Main.lambda$main$0` | 13   | Method invocation on null `tracker` reference |
| n/a    | n/a                  | n/a  | n/a                                           |

**Guarantee that is missing** *(what should be atomic, ordered, or protected):*

None at the program level. `Thread.start()` already gives a happens-before edge, so `tracker` is safely visible to `t1` even without `final`. The missing guarantee is in the tool's handling of lambda capture, not in the Java memory model.

**Buggy interleaving** *(2 to 4 steps)*

n/a — the failure is not caused by a concurrency interleaving between conflicting shared accesses.

**Why this produces the JPF symptom:**

In the source program, `tracker` is initialized with:

```java
DelegatingDeviceTracker tracker = new DelegatingDeviceTracker(initial);
```

and is never assigned `null`. Nevertheless, JPF reports that the receiver of `updatePosition()` in `Main.lambda$main$0` is null.

A lambda capturing `tracker` compiles to `invokedynamic`, and JPF synthesizes a `Main$$Lambda$0` class to carry the captured value. The null receiver inside the synthetic body suggests the captured `tracker` was not propagated correctly. This is an inference from the stack trace and from the fix (anonymous classes, which use ordinary constructor and field capture, eliminate the error). The exact JPF mechanism was not verified.

There is no evidence in the supplied source that the application itself contains a null dereference at this point.

## 4. Suggested solution

**Fix type**

* [ ] Add or widen synchronization (synchronized / lock)
* [ ] Use an atomic or concurrent class
* [ ] Add volatile
* [ ] Change lock order / lock granularity
* [ ] Fix wait/notify (condition loop, notifyAll, missing signal)
* [ ] Thread confinement or immutability
* [x] Other: **Avoid the problematic lambda/captured-reference representation (use explicit `Runnable` implementations)**

**Where to apply it** *(file:line range)*:

`Main.java:12-19`, covering both lambdas: `t1` (lines 12-15) and `t2` (lines 16-19). `t2` uses the same construct and would fail the same way.

**Description of the fix:**

Replace the lambda expressions with explicit `Runnable` implementations (anonymous classes or named classes), so that the `tracker` reference is passed through an ordinary synthetic field/constructor instead of being captured by a lambda.

The fix also declares `tracker` as `final`. This is cosmetic, since the variable was already effectively final. The behavioral change is lambda → anonymous class. Compiling with `--release 8` alone does not help, because lambdas still use `invokedynamic`.

**Code sketch**

```java
// before

Thread t1 = new Thread(() -> {
    tracker.updatePosition("G1", "Room3");
    System.out.println("G1 position: " + tracker.fetchPosition("G1"));
});

Thread t2 = new Thread(() -> {
    Map<String, String> snapshot = tracker.getAllPositionsStatic();
    System.out.println("Snapshot: " + snapshot);
});
```

```java
// after

final DelegatingDeviceTracker tracker = new DelegatingDeviceTracker(initial);

Thread t1 = new Thread(new Runnable() {
    @Override
    public void run() {
        tracker.updatePosition("G1", "Room3");
        System.out.println("G1 position: " + tracker.fetchPosition("G1"));
    }
});

Thread t2 = new Thread(new Runnable() {
    @Override
    public void run() {
        Map<String, String> snapshot = tracker.getAllPositionsStatic();
        System.out.println("Snapshot: " + snapshot);
    }
});
```

**Why it removes the symptom:**

n/a as an interleaving fix — this is not an interleaving bug. An anonymous inner class compiles to an ordinary class (`Main$1`, `Main$2`) that stores `tracker` in a synthetic field set through its constructor. This uses plain `new`, `putfield` and `getfield` bytecodes, avoiding the lambda-generated bytecode/captured-reference path that appears to produce the null receiver under JPF.

**Validation:**

Fix applied (lambdas → anonymous `Runnable`s, no logic change): the reported NPE no longer occurs. This supports the JPF-compatibility root cause.

**Other acceptable fixes** *(there is often more than one)*:

Use named classes implementing `Runnable`, or otherwise restructure the thread entry points so that the shared `tracker` reference is passed without lambda capture. Running with a JPF installation/configuration that handles lambdas correctly may also avoid the problem, but this was not tested.

**Invalid or superficial fixes for this bug:**

* Adding synchronization around `tracker`
* Making the reference a `volatile` field
* Adding `final` to `tracker` (already effectively final)
* Adding `Thread.sleep()`
* Changing `ConcurrentHashMap`
* Changing `HashMap`
* Removing `getAllPositionsStatic()`
* Reducing the number of threads
* Replacing `containsKey` + `put` with `replace` (valid hardening, unrelated to this error)

None of these addresses the reported null receiver.
