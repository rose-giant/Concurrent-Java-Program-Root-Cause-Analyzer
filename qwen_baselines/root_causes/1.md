## 3. Root cause

**Shared state** *(variable / object / lock):*

`CountingLanterns.asleep`, a mutable field of the single shared `CountingLanterns` instance `traveler`.

**Accesses involved**

| Thread   | Method               | Line | Operation (R/W/lock/wait/notify) |
| -------- | -------------------- | ---- | -------------------------------- |
| Thread-1 | `tryToSleep()`       | 5    | R (`while (!asleep)`)            |
| Thread-2 | `setAsleep(boolean)` | 20   | W (`this.asleep = value`)        |

**Guarantee that is missing** *(what should be atomic, ordered, or protected):*

The read and write of the shared variable `asleep` should be protected by a common synchronization mechanism so that the conflicting accesses cannot occur concurrently according to JPF's race-detection model.

**Buggy interleaving** *(2 to 4 steps)*

1. Thread-1 starts `tryToSleep()` and reads `traveler.asleep` while it is `false`.
2. Thread-1 continues looping and accessing the shared field.
3. Thread-2 finishes `Thread.sleep(500)` and executes `traveler.setAsleep(true)`.
4. Thread-2 writes `traveler.asleep` while Thread-1 is a runnable thread performing the conflicting read.

**Why this produces the JPF symptom:**

`traveler` is the same shared object used by both threads. `Thread-1` performs a read of `traveler.asleep`, while `Thread-2` performs a write to the same field. These accesses are not protected by a common lock, so `PreciseRaceDetector` reports a race on `CountingLanterns.asleep`.

## 4. Suggested solution

**Fix type**

* [x] Add or widen synchronization (synchronized / lock)
* [ ] Use an atomic or concurrent class
* [ ] Add volatile
* [ ] Change lock order / lock granularity
* [ ] Fix wait/notify (condition loop, notifyAll, missing signal)
* [ ] Thread confinement or immutability
* [ ] Other: n/a

**Where to apply it** *(file:line range)*:

`CountingLanterns.java:5` and `CountingLanterns.java:20`, protecting both accesses to `asleep` with the same lock.

**Description of the fix:**

Introduce a dedicated lock object, `asleepLock`, and synchronize both the read in `tryToSleep()` and the write in `setAsleep()` on that same lock. The lock must be scoped only around the individual field access so that Thread-2 can still acquire it and update `asleep`.

**Code sketch**

```java
// before

private volatile boolean asleep = false;

public void tryToSleep() {
    while (!asleep) {
        countSomeSheep();
    }
}

public void setAsleep(boolean value) {
    this.asleep = value;
}
```

```java
// after

private boolean asleep = false;
private final Object asleepLock = new Object();

public void tryToSleep() {
    while (true) {
        boolean isAsleep;
        synchronized (asleepLock) {
            isAsleep = asleep;
        }

        if (isAsleep) {
            break;
        }

        countSomeSheep();
    }
}

public void setAsleep(boolean value) {
    synchronized (asleepLock) {
        this.asleep = value;
    }
}
```

**Why it removes the interleaving:**

Both the read and write of `asleep` now require ownership of the same `asleepLock`. Therefore, the two conflicting accesses cannot overlap while executing the protected sections, removing the read/write interleaving that JPF reports.

**Other acceptable fixes** *(there is often more than one):*

A correctly scoped `synchronized` block using a common lock is an acceptable fix. Equivalent `java.util.concurrent.locks.Lock` usage can also provide the required mutual exclusion. A condition-based design using `wait()/notifyAll()` or `Condition` can be used as a redesign, provided the shared-state access is correctly synchronized.

**Invalid or superficial fixes for this bug** *(e.g. fewer threads, smaller workload, sleep, removed concurrency, one global lock):*

* Adding or increasing `Thread.sleep(...)` does not establish the required synchronization.
* Reducing the number of iterations or changing the timing does not fix the shared-state access.
* Removing one of the threads removes the concurrency rather than fixing the bug.
* Making `tryToSleep()` and `setAsleep()` entire `synchronized` methods is not an appropriate fix for this program because Thread-1 could hold the monitor while looping, preventing Thread-2 from acquiring it to set `asleep = true`.
* Adding `volatile` alone is not considered a fix for this JPF-reported case, since the provided experiment reports the same race with and without `volatile`.
