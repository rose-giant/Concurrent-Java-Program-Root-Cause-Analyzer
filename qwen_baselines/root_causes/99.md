## 3. Root cause

**Shared state** *(variable / object / lock):*

n/a as a concurrency bug.

The failing operation is class initialization of `java.util.concurrent.locks.ReentrantReadWriteLock`, triggered by the first `new ReentrantReadWriteLock()`.

**Accesses involved**

| Thread | Method                                                         | Line      | Operation (R/W/lock/wait/notify)                                 |
| ------ | -------------------------------------------------------------- | --------- | ---------------------------------------------------------------- |
| main   | `java.util.concurrent.locks.ReentrantReadWriteLock.<clinit>`   | 1504-1506 | Reflective lookup of `Thread.tid` fails (`NoSuchFieldException`) |
| n/a    | n/a                                                            | n/a       | n/a                                                              |

**Guarantee that is missing** *(what should be atomic, ordered, or protected):*

None at the program level. The read-write lock usage is correct: writes take the write lock, reads take the read lock, and every acquire is released in a `finally` block. The missing piece is in the tool: JPF's model of `java.lang.Thread` does not provide the `tid` field that the JDK's `ReentrantReadWriteLock` static initializer looks up.

**Buggy interleaving** *(2 to 4 steps)*

n/a. The failure occurs before any additional thread exists.

**Why this produces the JPF symptom:**

The JDK version of `ReentrantReadWriteLock` reads the thread id field of `Thread` through reflection and `Unsafe` in its static initializer. JPF does not run the real `java.lang.Thread`; it uses its own model class, and reflection on that class does not find a field named `tid`. As a result, the very first use of `ReentrantReadWriteLock` fails, regardless of how the lock is used afterwards. This is an inference from the stack trace. The exact JPF and JDK versions involved were not checked.

There is no evidence in the supplied source of an application-level defect.

## 4. Suggested solution

**Fix type**

* [ ] Add or widen synchronization (synchronized / lock)
* [ ] Use an atomic or concurrent class
* [ ] Add volatile
* [ ] Change lock order / lock granularity
* [ ] Fix wait/notify (condition loop, notifyAll, missing signal)
* [ ] Thread confinement or immutability
* [x] Other: **Avoid `ReentrantReadWriteLock`; use `synchronized` methods as the locking mechanism instead**

`synchronized` is used here as a substitute for the read-write lock, not to close a race. The original locking was already correct.

**Where to apply it** *(file:line range)*:

`ReadWriteMap`: remove the `lock` field and the `lock()/try/finally/unlock()` blocks, and mark each of the nine public methods `synchronized`. The source is on a single line, so line ranges are not meaningful. `Main` (the executor and the lambdas) does not need to change.

**Description of the fix:**

Declare `put`, `remove`, `putAll`, `clear`, `get`, `size`, `isEmpty`, `containsKey` and `containsValue` as `synchronized` and delegate directly to the wrapped map. Remove the `java.util.concurrent.locks` import.

**Code sketch**

```java
// before

private final ReentrantReadWriteLock lock = new ReentrantReadWriteLock();

public V get(Object key) {
    lock.readLock().lock();
    try { return map.get(key); } finally { lock.readLock().unlock(); }
}
```

```java
// after

public synchronized V get(Object key) {
    return map.get(key);
}
```

**Why it removes the symptom:**

n/a as an interleaving fix. The new class never touches `ReentrantReadWriteLock`, so its static initializer and the `tid` lookup are never executed. `synchronized` uses the monitor support that JPF implements natively.

**Validation:**

The supplied fixed version (`ReentrantReadWriteLock` → `synchronized` methods, same public API, executor and lambdas unchanged) is taken as passing JPF per the case record. This was not re-run here.

**Trade-off:**

Readers now exclude each other, so the concurrent-read benefit of the read-write lock is lost. This does not affect correctness, and the map remains fully protected.

**Other acceptable fixes** *(there is often more than one)*:

* A single `ReentrantLock` or `synchronized(lock)` blocks around each operation. `ReentrantLock` does not use the same `tid` lookup, but it was not tested under JPF.
* `Collections.synchronizedMap(map)` as the wrapper (untested here).

**Invalid or superficial fixes for this bug:**

* Using the fair mode, `new ReentrantReadWriteLock(true)` (same class initialization)
* Swapping read and write lock usage
* Adding more locking or `volatile` on top of the existing code
* Replacing the executor with plain threads, or changing the pool size (the failure happens before the executor is created)
* Replacing the lambdas in `main` (not involved in the failure)
* Adding `Thread.sleep()`

None of these avoids the failing class initialization.
